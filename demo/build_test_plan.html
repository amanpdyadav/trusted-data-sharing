4 · How we test

Six layers, from single functions to real attacks

The lower layers run on every change; the upper layers run at each checkpoint and write one row to results/history.csv. To avoid tuning to the test, detection is tuned on eight datasets and checked on the ninth and on the unknown HR file it has never seen; text rules are tuned on half of the labelled chats and scored on the other half.

Layer 1 · every change

Unit tests

  • ID-code checksum (all century signs), IBAN, card numbers, phone formats
  • Spoken numbers in Finnish, Swedish, English → digits
  • Same key + same input = same code; different key = different code

Pass: all green in pytest

Layer 2 · checkpoints

Detection accuracy

  • pets-eval detect against the field catalogue
  • Held-out dataset + unknown HR file as blind tests
  • Local AI kept only if it raises the score

Pass: F1 ≥ 0.85, sensitive-attribute recall ≥ 0.70

Layer 3 · checkpoints

Text redaction

  • pets-eval text on labelled chat and note spans
  • Recall weighted higher (F2): a missed ID is worse than an extra tag
  • Organisers’ hidden chat split at the end

Pass: recall ≥ 0.95 on names, phones, addresses, ID codes

Layer 4 · checkpoints

Release scorecard

  • pets-eval scorecard per case: HEALTH-S1, CS-S1, HEALTH-S2
  • Our own k and leak numbers must agree with it; a mismatch is a bug

Pass: research case composite ≥ 0.70, rows with k < 5 under 5%

Layer 5 · checkpoints

Attack replay

  • Re-run the two problem-demo chains on our release
  • Plus the organisers’ linkage attacks in the scorecard

Pass: every chain ends with 5 or more candidates

Layer 6 · hour 11

Real-data readiness

  • Runs with answer files hidden, network off, keys from environment
  • Same input + key gives identical output; 1.6M rows in minutes

Pass: every check in section 6 below
